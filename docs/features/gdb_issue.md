# libGdb エビデンス採取テストフレームワーク 設計メモ

GDB を使った C++ 単体検証で、エビデンス（証跡）作成を楽にするための
共通ライブラリ libGdb の検討記録。「やりたいこと / できていないこと /
これからの課題 / 懸念点」の4観点で整理する。

配置は SCRIPT 配下（`c_plus/cPlus_util/libGdb`）。版管理は現状どおり Git で
行う作業用ツール。**業務コード（特定の業務クラスや DB）には一切依存しない。**
検証対象は libGdb 内に自前で用意するモック処理とし、「テストデータを登録 →
条件で読み込み → 結果を観測」という典型的な読み込み処理を、外部依存なしの
インメモリ実装で再現する。

---

## やりたいこと

- **GDB のネイティブ出力に準拠したエビデンスを楽に採取する。**
  `(gdb) p 変数` → `$1 = ...` の型付き表示をそのまま証跡として残す。
  C++ 側で整形した文字列ではなく、GDB が実際にどう表示したかを証拠にする
  ことで、エビデンスの説得力を保つ。
- **対象ごとの記述量を減らす。** 新しい検証対象を追加するたびにゼロから
  書くのではなく、共通部分を libGdb に固定し、対象固有の部分だけを書けば
  よい状態にする。
- **libTree に倣った構成で整える。** 汎用部品はサブディレクトリ、対象固有の
  テストロジックはルート平置き、という切り分け。

### 部品の役割分担（狙う形）

| 部品                          | 内容                                                       | 汎用/対象依存            |
| ----------------------------- | ---------------------------------------------------------- | ------------------------ |
| ① main.cpp シナリオ           | ケースを実行順に並べ、`===== TEST: xxx =====` 見出しを出す | ほぼ定型                 |
| ② 対象別ロジック（xxxTest.*） | データ生成・対象への書き込み                               | 対象依存（書くのが本質） |
| ③ GDB観測点（ダミー関数）     | GDB がブレイクを張る着地点。処理はしない                   | 汎用化したい             |
| ④ dump_xxx.gdb                | ブレイク定義 + `p 式`。GDB出力がそのままエビデンス         | 対象依存（p式が本質）    |
| ⑤ gdb_common.gdb              | 共通設定 + ロギング（フラグで on/off、既定 off）           | 汎用（固定資産にしたい） |
| ⑥ gdb_run.sh                  | ランナー（引数で実行ファイル・gdbスクリプトを受ける）      | 汎用（固定資産にしたい） |

### 汎用化の狙い（方針として確定した内容）

- ⑤ **共通GDB設定** … `set pagination off` 等の定型。完全に対象非依存。
- ⑥ **ランナー** … 実行ファイルと gdbスクリプトを引数で受ける形にして汎用化。
  ```bash
  # gdb_run.sh <実行ファイル> <gdbスクリプト> [追加引数...]
  TARGET_EXEC="${1:?}"; GDB_SCRIPT="${2:?}"; shift 2
  gdb -q -x "$GDB_SCRIPT" --args "$TARGET_EXEC" "$@"
  ```
- **エビデンスのファイル出力はフラグ管理（デフォルト off）** … GDB の
  `set logging` によるファイル保存機構は導入するが、**フラグで on/off を
  切り替える**。既定は off で、あくまで「実行して GDB の出力を見る」ことが
  主目的。記録ファイルは主役ではない。フラグの外部設定ファイル読み込みは
  ログ機構本体に持たせず、別レイヤーの責務とする（機構本体はフラグ値を
  見るだけ）。
- ③ **GDB観測点の汎用化** … マーカー関数1個に集約する（下記）。

#### 観測点（③）の汎用化：テンプレートマーカー方式（`up` 不要）

観測点は「ブレイクの着地点」でしかない。当初は引数なしマーカー
`gdb_probe(const char* label)` で止め、`up` で呼び出し元フレームの実変数を
見に行く案を検討した。しかし `up` の段数はインライン展開・最適化で変動し、
対象が変わるたびに実機で段数を確認する必要があり、汎用化を阻害する。

そこで**観測対象を値としてマーカーに渡すテンプレート方式**を採用する。
テンプレートにすることで型は自動推論され、対象が変わってもマーカーは
書き直さなくてよい。観測変数がマーカー自身のフレームに存在するため
`up` は完全に不要になる。

```cpp
// libGdb 側に置く汎用マーカー（型非依存）。インライン抑止が重要。
template <typename T>
__attribute__((noinline)) void gdb_probe(const char* label, const T& value) {
    volatile const char* l = label; (void)l; (void)value;
}
```

```cpp
// テスト側は見せたい変数を渡して呼ぶだけ（型は自動推論）
// 読み込み対象は業務コードではなく、libGdb 内の自前モック処理
{
    std::vector<MockRecord> out;
    mock_read(key, out);          // 外部依存なしのインメモリ読み込み
    gdb_probe("out_dump", out);   // ここで停止。value=out がこのフレームに存在
}
```

```gdb
break gdb_probe
commands
  silent
  printf "(gdb) p value\n"
  p value            # value はこのフレームに存在。up 不要
end
```

これで③が完全に汎用化され、対象ごとに書くのは②データ生成・④p式・
①シナリオ配置の3つだけになる。

補足（テンプレートの注意点）:

- テンプレートはインスタンス化されて初めて実体が出る。各対象で実際に
  `gdb_probe(...)` を呼べば実体が生成され、`noinline` により関数として残る。
- `break gdb_probe` は各インスタンスへ pending で一括適用できる
  （`set breakpoint pending on` は共通設定側で有効化済み）。
- `value` が vector やメンバを持つ場合は、`value.size()` →
  `value[$i].xxx` の GDB ループ方式で各要素を p する。

## できていないこと（現状）

現物はまだ業務コードに依存した初期版の段階で、上記の汎用化・モック化は
未着手。到達点は「業務コードを一切使わず、自前モックだけで完結する」形。

- **③観測点が対象固有のまま。** 現状は業務固有のダミー関数で、引数も業務
  構造体の中身に依存している。汎用マーカー `gdb_probe`（テンプレート）は未導入。
- **⑤共通設定・⑥ランナーが未分離。** GDBスクリプトに共通設定とブレイク定義が
  混在。ランナーは実行ファイル名がハードコードされている。
- **エビデンスのファイル出力（set logging）が未実装。** 現状は画面出力のみ。
  フラグ管理での on/off 切り替え機構も未導入。
- **検証対象が業務コード依存のまま。** 現状はテストデータの登録・読み込みに
  業務・共通部品を介している。最終的には業務コードを一切呼ばず、libGdb 内の
  自前モック（インメモリのデータ登録・読み込み）で置き換える（未着手）。
- **ルート直下に旧世代・重複ファイルが残存。**
  - サブディレクトリ libGdb/ 側と重複する GDB スクリプト・ランナー
  - 現行 main.cpp と対応関数が不整合な旧世代の GDB スクリプト
  - 未参照 / 既に統合済みの旧ヘッダ
- **ビルド・動作確認が未実施。** Linux + g++ + gdb 前提（PostgreSQL は不要）
  のため Windows 環境からは検証できていない。現物が実際にビルド・実行
  できるかは実機で未確認。

## 懸念点（着手前に意識すべきリスク）

- **`up` の段数ずれ（テンプレート採用で解消）。** 当初案の「引数なしマーカー +
  `up`」は、`up` の段数がインライン展開・最適化（現 Makefile は
  `-finline-functions` 付き）で変動し、対象ごとに実機で段数確認が要る問題が
  あった。→ **観測対象を値として渡すテンプレート `gdb_probe(label, value)`**
  に変更し、`value` をマーカー自身のフレームに持たせることで `up` を廃止した。
  段数確定作業そのものが不要になる。テンプレートには引き続き
  `__attribute__((noinline))` を付け、マーカー自体の消失を防ぐ。
- **汎用化の限界は「p 式」。** 「何を証拠として見せるか」は対象ごとに違い、
  ここを無理に汎用化するとエビデンスの意味が失われる。p 式は対象依存のまま
  残すのが正解であり、これは制約ではなく設計判断。
- **GDB出力準拠とのトレードオフ。** C++ 側で整形して1本のテキストにすれば
  スクリプトはさらに汎用化できるが、GDB の型付き表示が失われエビデンスの
  説得力が落ちる。今回はGDB出力準拠を優先し、C++整形方式は採らない。
- **検証環境の制約。** ビルド・実行は Linux + g++ + gdb 前提
  （PostgreSQL は不要）。Windows 上では確認できないため、実装後の動作確認は
  実機（Linux）に依存する。
- **版管理は Git（確定）。** libGdb は現状どおり Git で版管理する。SVN や
  別の作業ツール置き場に移す必要はない。

## 設計判断の要点（記録）

- GDB出力準拠とエビデンス採取が最優先要件。この2点が「C++整形方式」を却下し、
  「マーカー + GDBネイティブ p」方式を選ぶ根拠。
- 観測点は**テンプレート `gdb_probe(label, value)`** に確定。対象を値として
  渡すことで型は自動推論され、マーカーは対象非依存の1個で使い回せる。
  `value` が自フレームに存在するため `up` は不要で、段数確定作業も消える。
- 汎用化の限界は「p 式（何を見せるか）」であり、本質的に対象依存。ここを
  無理に汎用化しない判断が、ツールの実用性を保つ。
- libGdb = 「エビデンス採取の型」を固定する層。対象ごとには「データ生成・
  観測点配置・p式」の3種だけを埋める運用。
- **ログはフラグ管理で on/off（既定 off）。** 主目的は「実行して GDB 出力を
  見る」ことであり、記録ファイルは副次的。ログ機構は導入するがフラグ値を
  見るだけとし、フラグの外部設定読み込みは別レイヤーに分離する。
- **検証対象は業務コード非依存の自前モックにする（業務クラスは一切使わない）。**
  特定の業務クラスや DB を呼ばず、libGdb 内の自前 POD 構造体とインメモリ実装で
  「登録 → 読み込み → 結果」という典型処理を再現し、それを検証対象とする。
  これにより外部依存なし・DB なしで検証でき、リファレンス実装にもなる。
- **版管理は Git で現状どおり。**
- 進め方は「共通資産を新設 → 自前モックで検証 → 旧ファイル廃止」。既存の
  業務依存コードへの載せ替えは行わない。
