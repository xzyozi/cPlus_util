# libGdb エビデンス採取テストフレームワーク 設計メモ

GDB を使った C++ 単体検証で、エビデンス（証跡）作成を楽にするための
共通ライブラリ libGdb の検討記録。「やりたいこと / できていないこと /
これからの課題 / 懸念点」の4観点で整理する。

配置は SCRIPT 配下（`c_plus/cPlus_util/libGdb`）。SVN 管理外・コミット対象外の
作業用ツール。現在の検証対象は `Cgt0927ChildResultKnr::readCalResult()`
（子プロセス計算結果の読み込み）。

---

## やりたいこと

- **GDB のネイティブ出力に準拠したエビデンスを楽に採取する。**
  `(gdb) p 変数` → `$1 = ...` の型付き表示をそのまま証跡として残す。
  C++ 側で整形した文字列ではなく、GDB が実際にどう表示したかを証拠にする
  ことで、エビデンスの説得力を保つ。
- **対象ごとの記述量を減らす。** 新しい検証対象（例: Cgt0928）を追加する
  たびにゼロから書くのではなく、共通部分を libGdb に固定し、対象固有の
  部分だけを書けばよい状態にする。
- **libTree に倣った構成で整える。** 汎用部品はサブディレクトリ、対象固有の
  テストロジックはルート平置き、という切り分け。

### 部品の役割分担（狙う形）

| 部品                          | 内容                                                       | 汎用/対象依存            |
| ----------------------------- | ---------------------------------------------------------- | ------------------------ |
| ① main.cpp シナリオ           | ケースを実行順に並べ、`===== TEST: xxx =====` 見出しを出す | ほぼ定型                 |
| ② 対象別ロジック（xxxTest.*） | データ生成・対象への書き込み                               | 対象依存（書くのが本質） |
| ③ GDB観測点（ダミー関数）     | GDB がブレイクを張る着地点。処理はしない                   | 汎用化したい             |
| ④ dump_xxx.gdb                | ブレイク定義 + `p 式`。GDB出力がそのままエビデンス         | 対象依存（p式が本質）    |
| ⑤ gdb_common.gdb              | 共通設定 + ロギング                                        | 汎用（固定資産にしたい） |
| ⑥ gdb_run.sh                  | ランナー（引数で実行ファイル・gdbスクリプトを受ける）      | 汎用（固定資産にしたい） |

### 汎用化の狙い（方針として確定した内容）

- ⑤ **共通GDB設定** … `set pagination off` 等の定型。完全に対象非依存。
- ⑥ **ランナー** … 実行ファイルと gdbスクリプトを引数で受ける形にして汎用化。
  ```bash
  # gdb_run.sh <実行ファイル> <gdbスクリプト> [追加引数...]
  TARGET_EXEC="${1:?}"; GDB_SCRIPT="${2:?}"; shift 2
  gdb -q -x "$GDB_SCRIPT" --args "$TARGET_EXEC" "$@"
  ```
- **エビデンスのファイル自動出力** … GDB の `set logging` で画面出力を
  そのままファイル保存。タイムスタンプ命名で実行ごとに証跡を残す。
- ③ **GDB観測点の汎用化** … マーカー関数1個に集約する（下記）。

#### 観測点（③）の汎用化：マーカー + up 方式

観測点は「ブレイクの着地点」でしかなく、引数の中身は本質的でない。GDB は
観測点で止まった後、呼び出し元フレーム（対象の実変数）を見に行ける。

```cpp
// libGdb 側に置く汎用マーカー（対象非依存）。インライン抑止が重要。
__attribute__((noinline)) void gdb_probe(const char* label) {
    volatile const char* l = label; (void)l;
}
```

```cpp
// テスト側は見せたい変数がスコープにある場所で呼ぶだけ
{
    std::vector<XXX_St> out;
    Cgt0928Foo::readXxx(key, out);
    gdb_probe("out_dump");   // ここで停止。out はこのスコープに存在
}
```

```gdb
break gdb_probe
commands
  silent
  up                 # 呼び出し元フレーム = out が見えるスコープ
  printf "(gdb) p out\n"
  p out              # GDBネイティブ出力 "$1 = ..." がそのまま
end
```

これで③が完全に汎用化され、対象ごとに書くのは②データ生成・④p式・
①シナリオ配置の3つだけになる。

## 懸念点（着手前に意識すべきリスク）

- **`up` の段数ずれ（最重要）。** `up` は「呼び出し元が1つ上のフレーム」を
  前提とする。インライン展開・最適化でフレーム構成が変わると `up` の段数が
  ずれ、意図した変数が見えなくなる。現 Makefile は `-finline-functions` 付き
  のため特に危険。→ 観測点を `__attribute__((noinline))` にして抑止する。
  それでも環境差でずれる可能性は残るので、実機で必ず確認する。
- **汎用化の限界は「p 式」。** 「何を証拠として見せるか」は対象ごとに違い、
  ここを無理に汎用化するとエビデンスの意味が失われる。p 式は対象依存のまま
  残すのが正解であり、これは制約ではなく設計判断。
- **GDB出力準拠とのトレードオフ。** C++ 側で整形して1本のテキストにすれば
  スクリプトはさらに汎用化できるが、GDB の型付き表示が失われエビデンスの
  説得力が落ちる。今回はGDB出力準拠を優先し、C++整形方式は採らない。
- **検証環境の制約。** ビルド・実行は Linux + g++ + gdb + PostgreSQL 前提。
  Windows 上では確認できないため、実装後の動作確認は実機に依存する。
- **SVN 管理外である点。** libGdb は現状コミット対象外の作業用ツール。
  資産として残すなら、どこで版管理するか（別の作業ツール置き場に含めるか）
  を別途決める必要がある。

## 設計判断の要点（記録）

- GDB出力準拠とエビデンス採取が最優先要件。この2点が「C++整形方式」を却下し、
  「マーカー + up + GDBネイティブ p」方式を選ぶ根拠。
- 汎用化の限界は「p 式（何を見せるか）」であり、本質的に対象依存。ここを
  無理に汎用化しない判断が、ツールの実用性を保つ。
- libGdb = 「エビデンス採取の型」を固定する層。対象ごとには「データ生成・
  観測点配置・p式」の3種だけを埋める運用。
- 進め方は段階移行（既存を壊さず共通資産を新設 → 載せ替え → 旧廃止）。
